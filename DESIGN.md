# Design System: Wager

## Overview

Wager uses a minimal, professional, sleek interface with refined light surfaces and a neutral charcoal web dark theme. Quiet green neutrals, careful spacing, and clear type hierarchy give customer tasks and technical diagnostics one consistent visual language.

The system is compact enough for event tables and inspection, with calm surfaces and generous grouping around customer actions. Content and state carry the visual interest; decoration must have a purpose.

**Key Characteristics:**

- Light green-neutral surfaces, neutral charcoal web dark surfaces, and subtle green action accents.
- Thin rules, flat panels, and restrained rounded controls.
- Inter for interface text; JetBrains Mono for IDs and code.
- Shared summary strips, form controls, and dialog treatment.

The native Android channel extends this approved system with phone-sized controls and automatic light/dark palettes. The web theme follows the OS until an explicit light/dark choice is saved; native-specific additions below describe the implemented mobile adapter.

## Colors

### Primary

Deep green identifies primary actions, links, selected emphasis, and focus. Its pale tint and soft border support resolved and provisional badges. The legacy emerald and blue button names both render the primary green; do not infer a separate brand palette from their names.

### Neutral

The app canvas is a faint green-gray with white panels and a slightly darker sidebar. Main, secondary, and muted text form the content hierarchy. Subtle borders divide panels and table rows; medium borders define fields. The frontmatter records the current shared web roles; namespaced web-dark roles override them in dark mode.

Semantic amber, violet, rose, and channel colors remain available for diagnostic meaning. Badges now consume shared semantic color roles, so their meaning remains consistent across both web themes.

**The Purposeful Color Rule.** Use green for actions and emphasis; reserve other accents for the existing semantic states and channels.

### Web theme refinement

Web dark surfaces are neutral charcoal: green is reserved for subtle accent, focus, selection, and semantic emphasis rather than tinting the entire canvas. Light mode keeps quiet green-neutral surfaces with clearer control borders and muted text. The native dark palette remains green-black and is not changed by this web refinement.

The theme control is a binary Light/Dark switch with an accessible switch role and checked state. Initial preference follows the operating system when no explicit saved choice exists. Clicking persists an explicit choice under `wager.theme`; OS changes apply while the preference remains system-derived, and storage events synchronize tabs. A head script resolves theme before CSS and React load to prevent a light startup flash. The visible control is a switch, not a three-option dropdown.

Theme changes transition palette properties (200ms) without animating layout; the thumb moves over (180ms). Reduced-motion preference removes theme and thumb transitions. Switching preserves all application workflows and state.

Current evidence is source inspection, eight passing contrast/bootstrap tests, and a successful production web build. Lint completes with warnings. Both listed source-review contrast findings were resolved. No current visual QA is claimed: earlier green-dark and dropdown screenshots predate the latest steering, and Computer Use was stopped by the user.

### Native palette extension

Native light mode reuses the web canvas, surface, text hierarchy, and primary green. Its subtle surface, border, warning, and error roles are separately namespaced in the frontmatter. Native dark mode uses green-black surfaces, pale green text and action emphasis, and an explicit dark on-primary color. Selection follows the operating system through `useColorScheme`; the web has its separate neutral charcoal dark palette.

### Call channel extension

The browser call simulator is an ordinary extension of this system: neutral light and charcoal surfaces, restrained green action emphasis, thin rules, and semantic error/warning feedback. Namespaced call light/dark tokens record the actual local stylesheet rather than changing existing web or native roles. Its binary dark switch persists the call channel's appearance choice; do not infer the web provider's cross-tab behavior from this separate implementation.

## Typography

Inter is the display and body family, with system sans fallbacks. The legacy serif alias also resolves to Inter. JetBrains Mono is reserved for IDs, envelopes, and code. Tables and times use tabular numbers.

The frontmatter records the desktop landing display, portal heading, card title, body, and field label roles. Portal supporting copy uses text (14px) with line height (1.65); table headers and metadata use compact text (11px), and portal table cells use readable compact text (13px). These are deliberate density differences, not a second typography system.

**The Interface Type Rule.** Keep navigation, headings, buttons, labels, and prose in Inter. Use monospace only where the content benefits from fixed-width characters.

### Native typography evidence

Mobile currently uses React Native platform-default text fonts: its shared primitives and router do not load Inter or JetBrains Mono or declare a font family. This is a recorded platform difference from the approved web type pairing, not a new brand font rule. Native typography roles record actual sizes, weights, and line heights without claiming a custom font is installed. In native implementation, documented pixel-like dimensions correspond to React Native logical layout units.

Display heading sizes are explicitly adjusted at the responsive breakpoints; the frontmatter display role is the wide-screen base.

### Native phone layout

Screens scroll within safe areas, with content padding (24), bottom content padding (48), a shared gap (28), and a centered maximum width (720). The four native tabs are Home, Conversations, Support, and Account; items have a minimum height (48), green active emphasis, muted inactive labels, a surface background, and a top rule. Header shadows are disabled. Stack routes provide connection, persona sign-in, conversations, support inquiry, and session linking. This is a native phone layout, independent of the web CSS breakpoints.

### Call console and transcript layout

The desktop-first call surface has a centered shell capped at (1160px), desktop side gutters totaling (80px), and a compact ruled header (94px minimum). Its workspace uses two columns: a console (330px to 420px) and a flexible transcript/context area, separated by (28px). Both panels use a local rounded outline (18px) without ordinary panel shadows. The call console starts with padding (28px) and minimum height (620px); active-call CSS compacts padding to (22px 26px), identity into a small icon/text grid, the digit field to height (46px), and keypad targets to minimum height (44px).

The stylesheet collapses the workspace to one column on narrow screens, removes the console minimum height, keeps the transcript scrollable, and stacks the footer. These are source-defined responsive behaviors, not a claim that the current narrow layout was visually verified.

## Elevation & Depth

Panels and buttons are flat. Tonal surfaces, thin borders, and interior rules establish grouping. Active sidebar items and the selected segmented option have a very small shadow. Dialogs use the theme-aware large shadow over a dim overlay without backdrop blur: light (0 18px 56px rgba(14, 24, 18, .16)), dark (0 18px 56px rgba(0, 0, 0, .3)). The base shadow token vocabulary remains in the stylesheet, but the final shared card rule removes card shadows.

**The Flat Panel Rule.** Keep ordinary cards, summary strips, and buttons free of shadows; reserve pronounced elevation for overlays.

Native panels likewise specify no shadow or Android elevation; surface tone and a thin border carry grouping. Feedback floats above the tab region through position and inverse colors rather than a declared drop shadow.

## Shapes

Controls use the effective compact control radius from the frontmatter, overriding the base medium radius. Web cards, summary strips, support containers, and dialogs use the extra-large radius. The large radius remains a shared primitive. Badges and status dots are fully rounded. Internal summary cells and support rows have square corners inside their shared rounded container. Rules are generally (1px).

Native touch controls and fields retain their explicit mobile control radius (12), while panels retain the extra-large radius (16). This larger control geometry adapts the same restrained rounded language to touch. Feedback uses the separately recorded mobile feedback radius.

## Components

### Buttons

Compact, restrained controls use medium weight (500) and minimum heights of (40px), with small (36px) and large (46px) variants. Primary buttons darken on hover. Secondary, outline, and ghost buttons gain a neutral hover surface and medium border. Active buttons dim slightly. Disabled and loading buttons use opacity (0.6). Keep the visible keyboard focus outline (2px) with offset (3px).

### Chips

Status badges pair a small colored dot with readable title-case text, a pale background, and a thin semantic border. The minimal variant uses text and dot without a capsule. Resolved and provisional badges share green surfaces but preserve different state dots. Channel badges retain their existing semantic colors.

### Cards / Containers

White panels use a subtle stroke, clipped rounded corners, and no shadow. Standard bodies use the frontmatter padding; headers and footers are separated by rules. Interactive cards change their border to the primary soft border and use a subtle neutral surface on hover.

### Inputs / Fields

White fields use a medium stroke, compact radius, and minimum height (38px). Labels sit above the field; helper and error messages sit below. Hover strengthens the border and focus turns it green, with the shared keyboard outline. Error fields retain an error border and message; do not discard error text when adding focus styling.

### Navigation

The quiet sidebar has compact rows with a white selected surface and dark green text. Hover uses a slightly darker green-neutral surface. The mobile bottom navigation retains four destinations and safe-area padding. Tabs scroll horizontally when necessary and preserve readable single-line labels.

### Summary strips and support rows

Account metrics and diagnostic metrics use the same segmented panel language. Support actions use ruled rows with a title area, explanation, and action area. Preserve their responsive stacking rather than making each cell an independent raised card.

### Dialogs

Dialogs share white surfaces, compact fields, and divided header/body/footer regions. Content scrolls independently within a viewport-limited shell. Desktop header and body padding is (24px 28px), with footer padding (16px 28px); mobile padding contracts to (20px), and footer actions can wrap. Existing modal entry motion is a brief scale-in (180ms). Reduced-motion preferences suppress motion.

### Native primitives and continuity feedback

Native buttons have a minimum height (50), centered text (15, weight 600), and optional Ionicons or an activity indicator. Secondary buttons use the native subtle surface with primary text. Pressed opacity is (0.8); disabled or busy opacity is (0.5). Fields have a minimum height (52), labels above, error text below, theme-aware selection and placeholder colors, and top-aligned multiline content. Panels use a thin theme border, padding (20), and internal gap (16).

Native rows have a minimum height (64), vertical padding (16), an interior rule, optional icon, descriptive text, and a chevron when actionable. Pressed row opacity is (0.7). Offline feedback uses warning tones and shows queued-message counts; request errors use an alert text role. Dismissible feedback sits (96) above the screen bottom with side offsets (16), inverse text/surface colors, and a close target of at least (48). Keep actual pending, offline, and failure states visible.

Session linking includes a rounded camera region and a manual code path when scanning is unavailable. Device camera appearance, permission behavior, and installation are not established by browser preview.

## Do's and Don'ts

### Do:

- **Do** apply the shared green-neutral palette and Inter typography across customer and diagnostic screens.
- **Do** use thin dividers and flat panels to group information.
- **Do** preserve semantic dots, visible focus, error messages, and responsive scrolling.
- **Do** keep IDs and code in JetBrains Mono.

### Don't:

- **Don't** introduce purposeless decoration or visual clutter.
- **Don't** add shadows to ordinary panels or buttons.
- **Don't** turn every summary segment or support action into a separate raised card.
- **Don't** replace compact technical labels with monospace throughout the interface.
